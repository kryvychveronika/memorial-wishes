# Жива Пам'ять (Memorial Wishes) 🕯️

> **Платформа вшанування пам'яті полеглих захисників України через дію.**  
> Рідні та побратими публікують мрії та бажання, які воїн не встиг здійснити у житті. Волонтери та небайдужі люди беруть ці бажання в роботу, втілюють їх у життя в пам'ять про Героя та надсилають фото-звіти родинам.

## 🌟 Про продукт та ідею

Більшість ініціатив пам'яті обмежуються свічками в соцмережах або грошовими донатами. Багато людей прагнуть зробити щось щире, особисте та змістовне, але не знають, як саме. Водночас родини захисників хочуть бачити, що пам'ять про їхніх близьких жива і продовжує надихати світ.

**«Жива Пам'ять» вирішує ці болі:**
1. **Перетворює скорботу на дію:** з'їсти піцу в Римі, побачити море в Одесі, пробігти півмарафон чи подарувати книги рідній бібліотеці воїна.
2. **Єдиний дім для спогадів:** впорядкований каталог карток захисників із фільтрами за містом, категорією та фінансовою складністю (безкоштовно / потребує коштів).
3. **Захист від дублювання («Я виконаю»):** бронювання бажання за волонтером, щоб уникнути плутанини.
4. **Зворотний зв'язок для сім'ї:** публікація звіту з фото та щирими словами подяки.

## 🏗️ Архітектура та технічні рішення

### 1. Frontend ↔ Backend (REST API)
* **Вибір:** REST на базі Django REST Framework.
* **Чому:** Передбачуваність статус-кодів (`200 OK`, `201 Created`, `400 Bad Request`, `401 Unauthorized`), нативне браузерне кешування та швидка розробка без оверхеду складних схем GraphQL.
* **Основні ендпоінти:**
  * `POST /api/auth/register/` & `POST /api/auth/login/` — реєстрація та авторизація через Token Auth.
  * `GET /api/wishes/` — отримання каталогу з фільтрацією (`category`, `difficulty`, `city`, `status`, `search`).
  * `POST /api/wishes/` — подача бажання родиною воїна (згода родини обов'язкова).
  * `POST /api/wishes/<id>/claim/` — резервування бажання авторизованим волонтером.
  * `POST /api/wishes/<id>/unclaim/` — скасування резерву та повернення в каталог.
  * `POST /api/wishes/<id>/complete/` — надсилання звіту з фото та текстом.

### 2. Backend ↔ Google Calendar (Синхронізація подій)
* **OAuth token:** Google OAuth 2.0 із скоупом `calendar.events`. Зберігаються лише зашифровані токени доступу.
* **Event write:** При натисканні «Я виконаю» та додаванні в календар автоматично створюється подія з датою та посиланням на історію воїна.
* **Push Notifications / Webhooks:** Google надсилає сповіщення про зміну події у календарі волонтера.
* **Обробка 5-хвилинного лагу:** Запланований фоновий воркер синхронізує стан раз на 5 хвилин для згладжування затримок вебхуків.

### 3. Backend ↔ Database: Що зберігається, а що свідомо НЕ зберігається
* **Зберігається:**
  * Хешовані паролі волонтерів (PBKDF2/Argon2 — паролі у відкритому вигляді **ніколи** не зберігаються).
  * Публічні дані про захисника, на які **родина надала пряму згоду**: ім'я, позивний, фото, підрозділ, текст мрії.
  * Тексти та фото звітів волонтерів.
* **Свідомо НЕ зберігається (Privacy & GDPR):**
  * Будь-які чутливі документи, свідоцтва або персональні контакти родин поза рамками модерації.
  * Інші приватні події календаря користувача (бекенд оперує виключно `event_id` створеної пам'ятної події).

### 4. CI/CD & Деплой (Коміт → Працююча версія)
* **Пайплайн:** `git push origin main` → **GitHub Actions** запускає тести бекенду та збірку фронтенду → Збірка Docker-образу → Автоматичний деплой.
* **Час деплою:** ~3-7 хвилин (вимога: менше 30 хв).
* **Rollback:** менше 2 хвилин через перемикання ревізії у Render/Cloud Run в 1 клік.

### 5. Backend → Поштовий сервіс (Transactional Email)
* **Коли надсилаються листи:** підтвердження реєстрації, схвалення бажання родини, взяття бажання волонтером, надходження звіту.
* **Стійкість до збоїв:** Листи надсилаються асинхронно через чергу задач. У разі недоступності поштового провайдера вмикається **exponential backoff** (повтор через 1 хв, 5 хв, 15 хв). Користувач не блокується і не отримує помилки 500.

## 🚀 Як запустити локально

### Варіант А: Через Docker Compose (Найпростіший спосіб)

Потрібен встановлений Docker:
```bash
git clone <URL_РЕПОЗИТОРІЮ>
cd memorial-wishes/infra
docker-compose up --build
```
* Фронтенд доступний за адресою: `http://localhost:3000`
* Бекенд API доступний за адресою: `http://localhost:8000/api/`
* Django Admin: `http://localhost:8000/admin/` (логін: `admin`, пароль: `admin123`)

---

### Варіант Б: Запуск вручну (Без Docker)

#### 1. Бекенд (Django)
```bash
cd backend
python3 -m venv venv
source venv/bin/activate       # На Windows: venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py seed_wishes   # Заповнює базу реальними прикладами
python manage.py runserver
```
API буде працювати на `http://127.0.0.1:8000/`.

#### 2. Фронтенд (React + Vite)
У новому вікні терміналу:
```bash
cd frontend
npm install
npm run dev
```
Відкрийте у браузері: `http://localhost:3000` (або `http://localhost:5173`).

## ☁️ Інструкція з деплою у хмару (HTTPS)

### Деплой Бекенду та БД (Render.com):
1. Зареєструйтесь на [Render.com](https://render.com).
2. Натисніть **Blueprints** → **New Blueprint Instance**.
3. Підключіть цей репозиторій GitHub та вкажіть шлях до файлу: `infra/render.yaml`.
4. Render автоматично створить керовану базу даних PostgreSQL та веб-сервіс Django з безкоштовним SSL/HTTPS сертифікатом.

### Деплой Фронтенду (Vercel):
1. Зареєструйтесь на [Vercel.com](https://vercel.com).
2. Натисніть **Add New Project** та виберіть цей репозиторій.
3. Вкажіть **Root Directory**: `frontend`.
4. Додайте змінну оточення:
   * `VITE_API_URL` = `https://<ВАШ_БЕКЕНД_НА_RENDER>.onrender.com`
5. Натисніть **Deploy**. За 1 хвилину ви отримаєте активне посилання з HTTPS!
